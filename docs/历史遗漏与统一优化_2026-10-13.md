# 历史遗漏与统一优化（2026-10-13）

当前构建 `UCE-Revision=2026.10.13.2`，兼容版本仍为 1.0.0。本轮覆盖动作执行、请求/响应编辑、规则存储、Montoya 映射、实时流量和发布校验；主 Java 代码净减少 344 行。未改变用户规则文件或启用状态。

## 问题与修复

| 问题 | 修复 |
|---|---|
| 外部客户端初始化失败回退模拟 crypto，可能生成假成功 | 去除生产回退；内部独立运行，外部明确不可用 |
| 外部不可用导致整个 crypto/signature 处理器也不可用 | 判断落到具体操作，不影响内部 AES/HMAC/编码 |
| 签名查密钥异常被吞掉 | 返回明确的 lookup 原因，避免统一“取不到密钥”掩盖问题 |
| 请求无实际 editor-send 加密仍可能写回编辑明文 | 与响应统一显式正文加密资格及实际结果检查；无动作/noChange/空结果不写回 |
| READ_ONLY 请求可被程序式文档变化标记为可发送修改 | 修改状态与准备入口都检查可编辑资格 |
| 请求/响应准备密文不感知规则更新 | 根据 RuleManager revision 失效；规则变化中生成的结果不缓存 |
| wire/editor/preview 三套输入与结果逻辑逐渐分叉 | ActionPipeline 统一 Header/变量/正文/bytes/noChange；保留 wire 继续与 editor 停止策略 |
| charset Header 变动后正文文本与字节不一致 | 同一原始字节按新 charset 重解释，后续步骤读取一致 |
| 失败签名临时 Header、失败脚本的共享变量赋值影响后续动作 | 失败步骤恢复 Header 与共享变量顶层绑定；既有成功结果保留 |
| Montoya 映射重复且请求编辑未使用实际 bytes | HttpContextMapper 共用映射，统一原请求 Header、工具来源与大小写重复头策略 |
| Content-Length 重复修正、实时流量可能显示旧长度 | HttpFraming 共用一次规范化；线上汇总记录在规范化后生成，编辑器完成 Header 写回后再次核对实际字节长度；原始无变化报文不修正 |
| chunked 通过 contains 判断可能误判 not-chunked | 按逗号分隔的完整 token 判断 |
| setConfig 保留调用方不可变 Map，后续 setConfig 抛异常 | 创建属于动作本身的可变配置副本 |
| “深复制”仍共享 headerTemplates 等嵌套对象，取消编辑可能影响原规则 | 深复制 JSON Map/List/数组；RuleManager 读写及分类查询隔离对象 |
| setRules 先清空再校验，失败丢失内存旧规则 | 全部校验及复制后再整体提交；失败保留旧规则和 revision；一次发布完整副本，并发读取不出现空列表 |
| 启用/禁用规则没有发送变更通知 | 统一发布副本、更新 revision 并通知，已准备的密文立即失效 |
| 切换语言后历史流量的方向/结果仍是旧语言 | 刷新现有行并保留选中记录；去除选择路径的宽泛静默 catch |
| 构建能力标记正确但仍是旧 revision 的 JAR 可通过发布 | 最终 build、make verify、status、release 核对预期 revision；维护测试不再硬编码日期 |

## 保留的兼容行为

RSyntaxTextArea 的类加载器/键盘映射隔离、报文前缀恢复和 Pretty/Raw 的原文保持，都有明确回归支持，本轮保留。always 不进入 response-editor-send；响应只展示仍只用 response-display，客户端继续接收密文。wire 失败仍跳过该动作并继续，失败原报文可以继续发送，不能把本次优化理解成阻断发送。

## 规则与部署

原已配置 actionType=encrypt、targetType=body/field、editor-send 的请求规则无需因本次修复修改；仅 display 解密现在只读。历史脚本若把加密标为 execute，需手工改为 encrypt，并保证条件覆盖编辑后的明文/头部。响应沿用明确 encrypt/body-or-field/response-editor-send。没有自动迁移现有规则。

重新加载新版 JAR 后，启动日志的 revision 应为 2026.10.13.2。已准备密文在规则变更时重新计算；仅重复读取而规则/文档未变时继续复用，避免重复随机加密。

## 验证

完整构建：344 项单元测试、2 项打包集成测试、最终 JAR 18 项密码检查通过。新增测试包含真实 Rhino/AES-GCM/HMAC 与独立 JDK 结果比对；状态/失败测试不靠 mock crypto 证明密码正确。10 组标准示例与 forward-test 在 source/packaged 各 34/34 通过；发布维护脚本 7 项回归通过。

未在运行中的 Burp 操作 Send/Forward，未发送真实网络请求。结构化上下文仍是单值 Header 模型，不能作为完整重复头/HTTP2 元数据抓包；明文文本编辑不保证任意二进制往返。处理器的本地失败恢复针对 Header/共享变量顶层绑定，不回滚共享对象内部任意变动或真实外部服务副作用。

HEAD/304 仅改 Header 时保留表示资源大小的 Content-Length，不按空正文改成 0。签名若依赖最终长度等自动维护的 Header，规则须在签名前明确准备这些依赖并复核最终报文字节，不能仅以签名步骤成功认定线上验证成功。
