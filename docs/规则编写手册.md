## 推荐工作流

1. 从客户端代码或协议取得 key/KDF/salt/IV/tag/AAD/封装等准确参数，不凭密文猜测。
2. 明确“只展示”还是“真实改写”。请求 display、响应 response-display 只用于页签；send/response-send 改流量。
3. 生成版本化导入 JSON，规则默认禁用，匹配范围限制到目标业务。
4. 准备脱敏固定向量和失败/非目标样例，用插件真实处理器验证。
5. 导入并核对差异，再按用户授权启用及实机验证；保留未验证部分的说明。

## 明文页签显示

Universal Crypto 请求和响应页签默认显示原始请求行/状态行、完整头部与明文正文。在正文区域右键，取消勾选“Show original HTTP headers”可切换为仅正文，再次勾选恢复完整视图。可编辑请求支持修改请求行、头部和正文，切换保留全部修改。Content-Length 初始为原报文值，发送时由 Burp 按加密后的正文重新计算，正文单独参与加密。HTTP 头、JSON 自动高亮并显示行号。有效 JSON 默认展开，右键 `Pretty JSON` / `Raw` 切换；无效 JSON 和普通文本保持原样。展示格式化不会改变未编辑的原始明文，实际编辑 Pretty 正文后则按编辑后的文本发送（包含展示空白）；签名依赖精确空白时，请先切换 Raw 再编辑。

仅展示的 Header 处理可在 `display` / `response-display` 阶段使用 `targetType=header`、`targetName=*`。脚本会分别收到每个 Header 值，替换结果只用于 Universal Crypto 编辑器渲染；请求/响应对象、发送中的请求和转发响应保持原值。正文与 Header 的匹配条件不同，需要同时覆盖两者时，使用任一 Header 通配条件的规则和正文 `contentPattern` 规则，并确保所有动作只使用展示阶段。

## 离线命令

在插件仓库先执行 `mvn package`，然后：

```bash
python3 skills/universal-crypto-rules/scripts/check_rule.py \
  --project . \
  --rules skills/universal-crypto-rules/assets/examples/03-pbkdf2-aes-gcm.rules.json \
  --fixtures skills/universal-crypto-rules/assets/examples/03-pbkdf2-aes-gcm.fixtures.json
```

默认 source 模式使用当前编译类；加 `--runtime packaged` 验证实际发布单 JAR。当前修复包保留并独立加载嵌入式原始签名 BC（Manifest `Crypto-Provider-Layout: signed-bc-nested-v1`），示例 02 内置 AES-CBC 和 06 内置 HMAC 签名已通过 packaged 验证。旧合并 BC 的 fat JAR 会影响受 javax.crypto 门控的 AES/SM4/DESede、HMAC、PBKDF2 等。SM2 密钥加载已独立改为 EC + sm2p256v1；BC 1.70 本身的 SM2 工厂别名仍不存在。完整新旧边界见验证文档。

去掉 fixtures 参数仅做导入格式、字段和动作配置验证，不执行脚本。工具使用真实 Rhino、匹配引擎、HTTP 拦截器和相位服务；不使用 mock 加解密，不访问用户配置或网络。fixture 模拟中启用的是临时内存规则，正式导入仍默认禁用。

## 安装与复用

仓库中 `skills/universal-crypto-rules/` 是完整可复制技能目录，含 SKILL.md、references、scripts、agents 与 assets。复制整个目录到目标 agent 支持的 skills 目录；Codex 使用 `~/.codex/skills/universal-crypto-rules/`（或其配置的 CODEX_HOME/skills）。技能在新会话加载后可显式调用：

> 使用 $universal-crypto-rules，根据以下客户端加密代码和报文生成可导入规则，并用真实引擎验证。

其他 agent 可以直接读 SKILL.md，无需 Codex 特定工具；运行验证器需要 Python 3、JDK 17+ 及当前插件构建产物。示例本身不依赖 Python cryptography，固定向量已包含在 fixtures 中。

## 维护与验证记录

详尽资料保持在技能 references 中，本页只提供入口，避免两份参数表漂移。接口改动时同步对应 reference 和示例向量。文档与工具不宣称未知协议、旧 JAR、未测试 JDK 或真实 Burp 流量必然适配。

BC/SM2 修复阶段验证：274 项单元测试、2 项独立 JVM 打包集成测试通过；最终单 JAR 的 BC 保留 2 张签名证书，18 项密码服务检查全部通过；9 组规则在 source/packaged 两种模式各通过 19 个用例，示例 06 精确核对签名头。独立 agent 原有规则及 8 个 fixtures 在新包重放 8/8 通过。SM2 使用 OpenSSL 独立向量并验证篡改拒绝。完整结果、原始日志和复核命令见 [修复后验证记录](../skills/universal-crypto-rules/references/validation.md#9-bc-打包与-sm2-修复后验证2026-10-10)。旧包的认证失败日志作为历史证据保留；未执行真实 Burp 流量验证。

当前构建：344 项单元测试、2 项打包集成测试通过，最终包 18 项密码回归仍全通过；请求编辑器保留请求行、头部及正文修改，切换不触发规则，发送规则读取修改后的请求信息。见 [当前验证记录](../skills/universal-crypto-rules/references/validation.md#23-历史遗漏与统一处理链2026-10-13)。

明文页签深色配色参照 Burp 原生 Pretty：HTTP 头名浅蓝、JSON 字段名黄色、字符串绿色、数字蓝色、布尔值和 null 橙色，正文背景为深灰。浅色主题使用相应的深色文字保证对比度。

请求/响应明文页签的字体、字号和字重读取 Burp 的 HTTP message display 设置（currentEditorFont），高亮 token 与行号使用同一字体；切回页签或加载新报文时刷新。不会固定为 12 号，也不会额外加粗。

Repeater 等可编辑请求窗口：解密成功且匹配 encrypt/body-or-field/editor-send 动作后，请求行、HTTP 头和明文正文均可编辑；默认光标位于正文，Cmd+A/Ctrl+A 或右键 Select all 选择当前完整视图。隐藏头部时仅显示及编辑正文，已修改的头部仍保留。发送时使用编辑后的方法、路径及头部匹配加密/签名规则，仅将正文交给加密处理。Host 的修改不会改变 Repeater 的连接目标，目标需在 Burp 中设置。只读窗口遵循 Burp EditorMode.READ_ONLY，响应页签在 READ_ONLY 模式保持只读；可编辑窗口需匹配显式 response-editor-send 正文加密动作才开放编辑。

插件重载后仍可编辑：明文编辑器使用独立的 keymap、InputMap 和 ActionMap，避免 RSyntaxTextArea 的全局缓存继续引用已卸载插件的键盘动作。无需重启 Burp 清缓存。

响应仅展示解密且客户端继续接收密文时，使用 `response-display`。原请求头参与 AAD/密钥派生时，脚本读取 `request.getOriginalHeader('X-Nonce')` 或 `request.getOriginalHeaders()`；`request.getHeader()` 在响应阶段仍是响应头。原请求头不并入响应条件匹配。已有 `response-send`/`always` 解密规则需手工迁移到展示阶段并更新取头代码，修复不会自动改当前规则。

`getOriginalHeader/getOriginalHeaders` 同时支持请求方向：读取本轮规则处理开始时的请求头快照；后续 Header 动作改变当前 `getHeader`，不改变快照。响应方向读取关联请求头，不保证是请求发送动作之前的值。

Repeater 请求预览/取值不会清除编辑状态，重复取值复用本次密文；再次编辑自动使缓存失效。Burp 设置新报文后才重置编辑状态，避免发送时回退到旧请求。

Proxy Intercept 响应编辑现已支持：保留 response-display 解密动作，另外添加 actionType=encrypt、targetType=body/field、executionPhase=response-editor-send 的响应动作。未修改时保留原密文；编辑后重新加密再提交；只有匹配加密规则才开放编辑。只读窗口仍不可修改，旧规则和当前用户配置不会自动迁移。

仅交付 JAR 和 Skill 时，用 check_rule.py --jar /path/to/plugin.jar 验证，不需要源码/Maven。步骤预览可填写原请求头，选择 response-editor-send；外部服务步骤明确未验证，不模拟成功。构建与同步命令见 [BUILD](../BUILD.md)。

请求编辑也要求明确的 `actionType=encrypt`、`targetType=body/field`、`executionPhase=editor-send` 动作，且条件须覆盖编辑后的明文、请求行及头部。仅 display 解密会只读展示；无动作、noChange、未实际改变正文或失败时保留原密文。历史脚本若用 execute 表示加密，需要改成 encrypt；原已正确配置 encrypt/editor-send 的规则无需因为本次修复修改。规则更新后重新生成准备密文，不再复用旧版本缓存。
